# TickLM-Bench: prior-art and claim boundary

**Research cutoff: 3 November 2026.** This is a targeted check of the primary arXiv records for the work most directly named in the benchmark plan. It is not a systematic literature review: I checked the records and abstracts, not every paper, released dataset, scorer, or license. Descriptions below follow the arXiv records at the cited versions.

## Closest work

| Work | Verified scope | Consequence for TickLM-Bench |
|---|---|---|
| [StreamDecisionBench: Evaluating Decisions in Force on Evolving Language Streams](https://arxiv.org/abs/2609.38612), submitted 29 Sep 2026, revised 9 Oct (v3) | Eight streaming scenarios across four application families; executable reference decisions from public rules; measures in-force accuracy across 0.5–8 second update intervals and separates judgment errors from latency errors. | Direct prior art for live decisions, stale outputs, and timing-aware correctness. Do not present those metrics or the general idea of testing decisions while evidence changes as new. |
| [TRACE: A Temporal Reasoning Benchmarking Framework for LRMs via Difficulty-controlled and Dynamic Test Generation](https://arxiv.org/abs/2607.04784), submitted 6 Jul 2026 | Models temporal reasoning as Allen interval algebra constraint satisfaction; dynamically generates graded tasks and checks reasoning with a trace-based oracle; reports 1,200 instances and eight evaluated reasoning models. | Direct prior art for generated, difficulty-controlled interval problems and trace/oracle evaluation. A new generator or exact oracle alone is not a novelty claim. |
| [QSTRBench: a New Benchmark to Evaluate the Ability of Language Models to Reason with Qualitative Spatial and Temporal Calculi](https://arxiv.org/abs/2605.18380), submitted 18 May 2026 | Covers Point Algebra, Allen's Interval Algebra, INDU, and multiple qualitative spatial calculi; varies symbolic and natural-language presentations. | Further overlap for interval and qualitative temporal reasoning, including presentation variation. Any such stratum needs explicit task-level comparison. |
| [TIME: A Multi-level Benchmark for Temporal Reasoning of LLMs in Real-World Scenarios](https://arxiv.org/abs/2505.12891), submitted 19 May 2025, revised 8 Oct 2025 (v4) | 38,522 question-answer pairs, three levels and eleven sub-tasks across Wiki, News, and Dialogue sets; focuses on dense temporal information, changing event dynamics, and social dependencies. | Broad real-world temporal question answering is established prior art. TickLM's synthetic rule-grounded episodes should not be described as the first benchmark for temporal reasoning in realistic language. |
| [What Really Controls Temporal Reasoning in Large Language Models: Tokenisation or Representation of Time?](https://arxiv.org/abs/2603.19017), submitted 19 Mar 2026 | Introduces MultiTempBench: 15,000 examples from 750 curated English questions, expanded across five languages, date arithmetic, time-zone conversion, temporal relation extraction, and Gregorian, Hijri, and Chinese Lunar calendars. | Calendar arithmetic, time-zone conversion, language variation, and date-format robustness are already studied. A narrower English-only suite should not claim these topics as new. |
| [AgentTime: Can Agents Estimate and Control Their Own Runtime?](https://arxiv.org/abs/2610.09944), submitted 7 Oct 2026, revised 8 Oct (v2) | 222 tasks from 18 sources test requested-duration following, runtime prediction, and elapsed-time estimation in native agent settings. | AgentTime directly covers self-runtime control in client harnesses. TickLM's intended live track instead concerns whether a decision is semantically valid as external state advances; keep those claims separate. |

## Defensible scope

The current plan combines several established areas: exact rule-grounded temporal episodes, paired counterfactual variants, raw versus primitive-derived inputs, model and client comparisons, and a separate live track. The review above found close work on each major topic, but did not find a cited benchmark that evaluates that exact combination under one protocol. That observation is a **candidate composition gap**, not evidence of novelty or priority. It should be retained only if direct comparison against the released tasks and scorers confirms it.

The strongest near-term contribution is therefore a reproducible comparative study: use paired cases to test whether a system updates its answer when a relevant time fact changes; separate raw from derived inputs without exposing the gold decision; report ordinary generated-answer scoring separately from exact-choice logits; and report snapshot semantic correctness separately from live publication validity and latency. StreamDecisionBench means the live metric itself cannot be claimed as new. TRACE and QSTRBench mean interval reasoning and generated exact-oracle questions cannot be claimed as new. The contribution, if supported, is the controlled cross-track comparison and its evidence, not a new umbrella category of “temporal reasoning.”

Before making a publication or state-of-the-art claim:

1. Compare the actual released TickLM tasks, splits, prompt renderer, answer parser, and oracle with the official TRACEBench, QSTRBench, TIME, MultiTempBench, and StreamDecisionBench artifacts. Record which tasks are reproduced and which only share a topic; do not call a custom score an official benchmark score.
2. Check each artifact's license and permitted redistribution before packaging data, prompts, or scorer code. The arXiv abstract alone does not establish the dataset's license or reproducibility.
3. Use fresh, sealed evaluation seeds or domains for final claims. Public generated cases, development sets, model selection, and repeated prompt tuning cannot establish resistance to contamination.
4. Describe model and harness coverage from actual completed runs. A public catalog, account configuration, client subscription, or available model name does not prove inference access or a completed evaluation.

## Paid-call ceiling caveat

The ledger's reservation is a local accounting guard, not a provider-enforced dollar ceiling. OpenRouter documents `max_completion_tokens` as the maximum completion tokens and marks `max_tokens` deprecated; the selected route still needs confirmed cap behavior, including how it counts billable reasoning tokens. The estimator additionally assumes UTF-8 prompt bytes plus 4,096 tokens cover all input and hidden overhead. That is an explicit reserve assumption, not a universal provider guarantee. OpenRouter's `provider.max_price` filters the per-million-token rates accepted for routing; it does not itself cap a whole request at a fixed dollar amount. The runner retains an unknown settlement as reserved, but currently continues to later cases when usage cost is missing; only a reported overrun blocks later reservations. A strict paid run therefore needs an operator-enforced stop on unknown usage, confirmed route limits, and the applicable external account/key spend control. See the [OpenRouter completion API reference](https://openrouter.ai/docs/api/api-reference/chat/create-a-chat-completion) and its [max-price routing explanation](https://openrouter.ai/blog/tutorials/how-to-get-the-lowest-cost-llm-inference-on-openrouter/).
