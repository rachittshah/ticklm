# Live clock evidence review: `live-clock-20261102-a`

This is a read-only review of `artifacts/live-clock-20261102-a/manifest.json`, `summary.json`, and `trace.jsonl`. The manifest's hashes for `realtime.py`, `live_worker.py`, `realtime_state.py`, `benchmark.py`, and `core.py` match the files reviewed here.

The run used the local Qwen3-4B abliterated 4-bit model with `clock_only=true`. The manifest requested 60 seconds, but the self-test completed after **8.345 seconds**. This is a short live exercise, not a completed 60-second trial.

## State handler and event-loop evidence

The run supports several narrow claims about the runtime:

| Check | Trace evidence | Result |
|---|---|---|
| Samples entered during real elapsed time | 61 records from `simulated_live_sensor`; `data_revision` runs consecutively from 1 through 61. | Passed |
| A deadline fired while generation was in progress | The trace orders the race request's first token, alarm injection, urgent deadline firing, and completed result. | Passed |
| Superseded generation was blocked | The race result returned after the `mode_changed` event and was rejected with `state_changed`. | Passed |
| Request expiry without a later semantic event | After `source_paused` at revision 7, the 0.3-second request expired with revision still 7. The last observation was 1.663 seconds old at the check. | Passed |
| Deadlines fired once | The trace has one `probe` firing and one `urgent` firing. | Passed |

The race's monotonic timestamps are strictly ordered:

| Event | Monotonic time (seconds) |
|---|---:|
| First token from the race generation | 48097.200800250 |
| Alarm event injected | 48097.204924375 |
| Urgent deadline fired | 48097.460090666 |
| Race generation completed | 48098.749571958 |

The urgent deadline fired **5.16 ms** after its scheduled time and about **1.29 seconds before** generation completed. The separate `probe` deadline was **6.48 ms** late. The observed event-loop interval p50/p95/maximum was 11.11/11.60/15.01 ms. These are measurements from this run, not scheduling guarantees.

## Language-model answerability

The runtime state was present in the prompts, but the model did not consistently apply it. The checks are simple string checks against the requested fixed-token answer; there was no language-model judge.

| Request | State supplied at request time | Model response | Review |
|---|---|---|---|
| Frozen clock control | Original snapshot showed `probe` pending with 3 seconds remaining. | `PENDING` | Correct for that frozen snapshot. It is intentionally stale relative to later live time. |
| Fresh clock | Captured 4.259 seconds after run start; `probe` was `fired`, with a `deadline_due` event 1.252 seconds old. | `PENDING` | Incorrect for the live snapshot. The response arrived after the deadline had fired. |
| Refresh after race | Current mode was `ALARM`; `urgent` was `fired`. | `ALARM; PENDING` | Mode was correct; deadline status was wrong. The result passed the state/revision validity check, which does not certify answer correctness. |
| Stale observation | The prompt stated that an observation older than 1 second is stale; the supplied age was 1.663 seconds. | `FRESH` | Incorrect. At publication the age was 1.986 seconds. |

The in-flight race answer described the old `NORMAL` snapshot and was rejected after the alarm changed the semantic revision. It also described a deadline event from 1.440 seconds earlier as “about to expire,” even though its captured deadline state already said `fired`. The publication guard worked; the generated text was not reliable temporal reasoning.

`all_checks_passed` is false: six of nine checks are true. Those passing checks establish that the clock and event machinery changed state, invalidated one stale response, and expired a request over time. The three model checks—fresh deadline answer, refreshed deadline answer, and stale-observation classification—failed.

## Scope and limits

- This artifact is a **clock-only** run. `predictive_wake` is null and there is no time-series foundation model (TSFM) forecast. It says nothing about TSFM value or a clock-only-versus-TSFM comparison.
- Sensor values were generated by the script at live monotonic times. Waiting and inference were real; the readings were simulated, not obtained from a physical sensor.
- The language model was not asked to report the current UTC timestamp or a numerical elapsed-time estimate. The run therefore does not measure those answer skills.
- This is one short run of one local model and one scripted scenario. It provides no statistical generalization, reliability rate, or hard real-time guarantee.
- The state-handler result and the model-answer result must stay separate: the runtime supplied and enforced temporal state correctly in the observed race, while the model misclassified supplied deadline and observation-age facts.

The injected-clock unit tests separately cover wall-clock jumps, monotonic deadlines, data-versus-semantic revisions, request expiry, run identity, and invalid sample ordering. They test deterministic state behavior; they do not establish physical-sensor correctness or general model temporal understanding.
