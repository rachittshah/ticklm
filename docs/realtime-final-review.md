# Independent review of the live-time prototype

Reviewed 2026-11-02 against the retained summaries and traces, the state guards, the live runner and its tests. This is a review of a local proof of concept. The clock and event loop supply time and observations to the frozen language model at inference; the results do not demonstrate a clock or continuous awareness inside the model weights.

## What was observed

- The final clock-only run [live-clock-20261102-d](../evidence/live-clock-20261102-d/) reports 10/10 scripted checks in 8.85 seconds. After a real wait, the model returned `EXPIRED` for the fired probe deadline and `4.500` for a snapshot elapsed time of 4.50013 seconds. This checks use of the supplied snapshot, not autonomous timekeeping between calls. The separate publication clock was later than the snapshot.
- In that run the worker's first token was timestamped at 49059.838372, the alarm arrived at 49059.848155, and the urgent deadline fired at 49060.102113 while generation was still in progress. Its observed deadline lateness was 3.95 ms. The old generation was rejected for a state change, and a later response reported `ALARM; EXPIRED`. After an actual pause in sample arrivals, the model reported the observation as `STALE`; a separate short-lived ticket expired without a semantic event.
- The final TimesFM-assisted run [live-fused-20261102-b](../evidence/live-fused-20261102-b/) reports 12/12 scripted checks over 24.69 seconds, with 201 ingested samples and seven language-model calls. The model returned `4.528` for a supplied snapshot elapsed time of 4.52773 seconds. The urgent deadline fired during actual generation, 0.45 ms after its scheduled monotonic time, and the prior result was rejected. Event-loop interval p95 was 12.82 ms and the largest observed interval was 17.34 ms. These are run-specific observations on a general-purpose operating system, not hard deadlines or worst-case bounds.
- The TimesFM call used 128 **regularly resampled values derived from live synthetic arrivals**, not necessarily 128 observations taken at exactly equal intervals. In this one run the forecast call took 67.39 ms, the cheap forecast took 3.71 ms, and their respective wake hints were 1.1 and 1.3 seconds. The trace records the forecast-origin-based scheduled wake and its later firing. This demonstrates the wiring and a single cost comparison, not improved prediction, fewer missed events, a scheduling advantage, or a physical sensor reading. The clock-only run already demonstrates the timer and stale-answer mechanism without TimesFM.
- Earlier [clock-only A](../evidence/live-clock-20261102-a/) and [B](../evidence/live-clock-20261102-b/) are retained failures with different prompts/checks. In A, the model missed all three deadline/freshness answers checked; B missed the fresh deadline answer. The later runs use a clarified deadline representation and different prompts, so their passes should not be presented as a reliability rate. The traces record synthetic sensor values emitted during real wall time, not measurements from an external device.

The summaries' elapsed-number check evaluates the exact supplied snapshot with a 0.15-second tolerance, and categorical checks reject negated/ambiguous strings. Neither establishes model arithmetic independent of the external clock: the current numeric elapsed value is already supplied in the prompt. The two scripted runs last less than the earlier proposed 30–90-second stress trial.

## Controls and remaining boundaries

The state tests cover independent monotonic and wall clocks under injected UTC jumps, new-data invalidation for observation-bound tickets, freshness-threshold crossing, and a pending deadline passing before a timer tick. Request IDs, run IDs, monotonic expiries and semantic revisions are explicit. The model worker is a separately spawned process; the event owner fires deadlines independently. Forecast wake times are anchored to the forecast context's end time and are bounded, with a ticket for semantic/expiry changes. The actual race is supported by timestamps showing first token, injected alarm, due deadline and model completion in that order.

The distinction between ordinary observations and semantic events matters: samples increment `data_revision`, but only tickets explicitly bound to observations reject a newer sample or freshness transition. A forecast ticket is time- and semantic-revision-bounded, not automatically invalidated by each new sample. Any narrative about a sample must be labeled as referring to its snapshot, and an independently captured publication clock cannot make the old narrative current. Whether a forecast remains useful under intervening small changes needs evaluation; this run alone does not validate that policy.

The initial review found that watch output printed rejected text even while labeling it `published: false`, and that opening the source after warmup discarded arrivals during loading. The subsequently updated code suppresses invalid text from user-facing output, labels valid narratives with a snapshot UTC time, and captures the initial EOF before warmup so later arrivals remain eligible for reading. **Retaining bytes does not preserve their original write times:** ingestion begins after warmup, and the protocol assigns times when records are read. A sample buffered during warmup can appear fresh even if it was written earlier; a relative deadline starts when ingested. Ordinary polling likewise provides read time rather than exact producer time. The source currently rejects supplied timestamps, so treat freshness and deadlines as relative to intake, not the external event's actual occurrence. Rotation or truncation deliberately advances to the new EOF: records already in a replacement file can be lost, and the source-reset trace now states that policy. Do not describe watch intake as lossless. The final traces were produced after these corrections.

The initial review also identified shallow sharing of nested deadline bounds between the returned ticket and the internal registry. A subsequent change deep-copies the stored identity fields, and a regression test mutates the returned nested expiry in place and expects rejection. The final trials were recorded after this correction.

The final clock-only D and fused B manifests record the same hashes for `realtime.py`, `live_worker.py` and `realtime_state.py`; those hashes also matched the files on disk when checked for this review. Earlier runs preserve their own manifests and should not be attributed to the final source. The opt-in real CLI watch integration [live-watch-20261102-b](../evidence/live-watch-20261102-b/) passed in 8.02 seconds: it ignored an existing backlog, accepted a sample, door event and 0.25-second deadline appended during actual model generation, rejected the old response, and later published a valid response. The recorded file deadline was 7.73 ms late. The test also checks that rejected output omits the text, and its stdout is retained. This single run does not validate warmup-arrival retention or the explicitly lossy rotation path.

## Appropriate claim and next gate

The supported claim is that, in these short local runs, an external runtime tracked real elapsed time and synthetic live changes, supplied snapshots to a frozen model, fired independent deadlines during generation, rejected one stale in-flight result, and used one time-series forecast to schedule a later wake. It does not establish continuous cognition in the weights, robust user-facing accuracy, reliable event ingestion across failures, calibrated forecasts, a TSFM scheduling benefit, or production/hard-real-time readiness.

Before a broader claim, extend the retained CLI watch evidence to warmup arrivals and source resets; repeat clock-only and forecast-assisted runs under the same schedule, including quiet intervals, event bursts and blocking generations; compare forecast wake policies to fixed and cheap-predictor baselines on measured misses, latency and cost; and test restart/suspend or mark their behavior unknown. Log failures as well as successes and preserve model, checkpoint and source identities for each run.
