# Real-time temporal bridge: architecture and evaluation review

This replaces the static-question objective for the next experiment. The goal is a system that can answer about the current time, elapsed time, recent events and deadlines while real time passes and events arrive. A frozen language model has no demonstrated awareness between calls: the operating system clock and the surrounding process must provide fresh state at inference time. The earlier forecasting QA results do not establish this capability.

## Cheapest correct architecture

1. Run a small event loop with a monotonic clock for elapsed durations, timer scheduling and local ordering, and a UTC wall clock for externally meaningful timestamps. Each accepted event gets an explicit ID, monotonic arrival time, UTC observation time, payload and increasing state revision. The exact clock and deadline calculations are deterministic; no model call is needed to know that ten seconds elapsed or a deadline is due.
2. Maintain a current snapshot with a run ID, clock-domain/boot identity, state revision, snapshot monotonic and UTC timestamps, event IDs and their ages, deadline state, and any derived numerical values. Pass a compact snapshot plus the user's question to the unchanged language model. Keep the original event log and exact prompt for verification. Fresh time is acquired on every request even when no event has arrived.
3. Dispatch inference outside the event-loop execution path. A separate worker process is the safest initial isolation for a potentially blocking model and GPU calls; verify actual event-loop lag rather than assuming a thread or Python callback stays responsive. The state owner retains a request ID, immutable snapshot revision, snapshot time, and maximum acceptable age. Never use a global latest response to pair a result with a request.
4. At publication, atomically compare the captured revision with current state and check the snapshot's elapsed age against the request's freshness limit. An event or deadline transition invalidates an answer based on older state; clock-sensitive answers can also expire solely because time passed even when the revision did not change. An expired or superseded result is explicitly rejected, not silently published. A bounded retry with a newly captured snapshot can be offered; if it cannot finish in time, report no fresh answer. Attach an `as_of` timestamp to answers that are only valid for the snapshot, and use deterministic current time for the publication timestamp. An `as_of` number is not a claim about the time at output unless recomputed or covered by the requested tolerance.
5. Execute deadline and alert transitions in the event owner, not in the language model or its worker. The language model may describe a deterministic action after it occurs; it cannot authorize the timer to wait. Record the scheduled deadline, actual dispatch time, lateness, event-loop lag and any miss. A general-purpose OS is not a hard real-time system, so make no zero-lateness or guaranteed-deadline claim.
6. TimesFM is optional and should predict a sampled changing signal, for example a future threshold crossing or a wake-up priority. It does not replace the clock or deterministic deadline. Compare a fixed-interval scheduler, a last-value/linear prediction scheduler and TimesFM at the same alert definition, horizon and permitted miss rate. Event arrival, deadline dispatch and a maximum wake interval remain independent of forecast. TSFM can propose an earlier check; it must not delay a mandatory check. Log its input history, output, selected wake and cost. Without a validated gain against cheap baselines, omit it from the default path.

**Existing bounded cost evidence:** v1's saved context-128/horizon-24 TimesFM forecast has 35 warm calls with p50 11.02 ms and p95 11.78 ms; the first call was 75.82 ms and loading 1.99 s. Its cheap forecaster had about 0.19 ms warm p50 over the same 35 stored calls. These are separate historical measurements, not end-to-end real-time latency, contention measurements, or evidence of a scheduling gain. A 30–90 second live stream cannot produce 128 one-second observations at startup: mark an explicitly supplied earlier seed history as synthetic/bootstrap, or wait until enough real samples exist. Never treat bootstrap values as live observations.

## Failure and clock semantics

- **No-input passage:** clock age and remaining time must change after an actual wait without incoming events. A changed event revision is not required for elapsed time to change.
- **Wall-clock adjustment:** an operating-system wall-clock jump must not make monotonic elapsed durations negative or trigger an elapsed deadline early. Record both clock values and the detected discrepancy; display wall time as an observation, not as a monotonic duration. Simulate forward and backward jumps with injected clocks in unit tests.
- **Restart, suspend and clock-domain change:** monotonic values cannot be compared across a reboot or an unknown boot/session identity. Persist UTC timestamps and deadline intent, detect the changed domain, and reconcile according to an explicit policy; if elapsed time cannot be established safely, mark it unknown and require reconciliation rather than fabricate a duration. Test both restart and any platform-specific suspend behavior; do not assume Python's chosen monotonic clock has a particular sleep behavior without measuring it.
- **Reordering and duplicates:** define event-time versus arrival-time semantics. Deduplicate by explicit event ID, preserve late events and their arrival time, and never rewrite past state silently. A newly accepted late event still increments the state revision and can invalidate in-flight answers.
- **Inference race:** an event or deadline transition after snapshot capture and before publication makes event-dependent output stale. Time-sensitive output has a separate expiry even if no event occurs. Publication check and state revision check must be synchronized with the state owner; checking once before inference is insufficient. Cancellation is an optimization, not the correctness mechanism.
- **Missing, blocked or slow models:** alarms continue without a model. Bound queue size and retry count, record timeouts and invalidations, and expose overload or stale output as such. Monitor event-loop lag during actual concurrent inference; do not claim concurrency based solely on separate tasks or processes.
- **Event completeness:** a source sequence number or expected input counter helps distinguish no events from a disconnected or lagging source. A stale/unknown source is not proof that nothing happened.

## Small live wall-time experiment

Run one reproducible **60-second actual wall-clock trial**, with a predeclared schedule and a durable trace. Every timestamp in the trace must come from the live run; simulated time is for unit tests only. Use one short generated stream with timestamped input events, at least one 8–12 second no-input interval, and an independent deadline during that quiet interval. Schedule questions that require current UTC time, elapsed seconds since run start, age of the last event, deadline remaining/overdue, and the latest event after an update. Grade numerical answers against the logged monotonic/wall-clock ground truth at the specified snapshot or output moment, using an explicit tolerance and an explicit time zone.

Evaluate paired arms on the same timeline and model, with matching question, schema, generation limit and as comparable a prompt length as practical:

| Arm | Input at request | What it isolates |
|---|---|---|
| Frozen snapshot | Initial timestamp and event state, never refreshed | Whether a static context becomes stale. It is an intentionally weak reference, not the strongest alternative. |
| Deterministic current state | Current clock, event ages, deadline and revision; no TSFM | Cheapest practical real-time baseline. |
| Current state plus TSFM | Same current state plus a labeled prediction of the sampled signal | Incremental value and cost of forecasting, if history is available. |

Do not claim a TSFM benefit if the deterministic current-state arm already answers the clock question. For elapsed and deadline arithmetic, also report the deterministic software answer, which should be the baseline to beat on accuracy and latency. For a stale/static arm, the passage of time is the intended intervention; differences show the utility of refreshed context, not learned clock awareness. Choose numerical grading tolerance before collecting answers and record parse failures as failures, not missing successes. Report the input clock snapshot separately from output time, so delay during generation cannot masquerade as accurate current time.

Include an intentional **in-flight event** trial. Start an actual streamed LLM generation, wait for an observable first-token or other verified generation-start signal, then inject a new event while generation is still running. Record event time, generation start/finish, snapshot revision, revision at completion and publication decision. The test only counts if the event is verified to arrive strictly between start and finish; otherwise report it as inconclusive and repeat within a fixed attempt limit. The prior response must be rejected or clearly marked stale. A separate no-input timeout test should expire a time-sensitive answer without any revision change. Verify the event loop fires the deadline while generation is active, rather than after generation completes. Retain one actual model text response and numeric grader result for every arm and every attempted race.

## Evidence and acceptance

Save an append-only, timestamped event trace containing run ID, source/event IDs, UTC and monotonic times, revision transitions, scheduled and actual deadlines, request and snapshot IDs, prompt, model path/revision, generation start/first-token/end, response, grader reference and tolerance, stale/expiry decision, retry, and measured event-loop lag. Preserve failed, late and inconclusive trials. Clock metadata and startup/restart identity belong in the run manifest. Redact user data only according to an explicit retention policy; synthetic test messages are preferable for the first run.

CPU-only tests with injected clocks must cover forward/backward UTC jumps, restart/domain mismatch, no-event expiry, event-during-generation revision change, deadline transition, duplicated and late events, and a model that blocks or never returns. A live test must then demonstrate the actual operating-system event loop, real passage of time, a genuine concurrent LLM generation and a retained trace; fake-clock tests cannot establish responsiveness. Report exact numeric accuracy, stale responses rejected, deadline lateness and missed deadlines, request latency, overhead, and any trial that failed to exercise the intended race. Success would establish bounded behavior for this local prototype under the tested load, not continuous cognition, hard real-time guarantees, or temporal awareness inside the frozen weights.
